# Автоматичний випуск EXE та Apps Script

Вихідний код застосунку зберігається у `source/`. Налаштування чинного
проєкту Google та розгортання — у `automation.json`; паролів у цьому файлі немає.
Оригінальна база комісії й адреса `/exec` закріплені в налаштуваннях.

## Одноразове підключення власника

Підключення Google Drive у ChatGPT не надає GitHub токен Apps Script.
Поточна інтеграція GitHub також не має дозволу керувати Actions Secrets
(API повертає 403). Власник один раз авторизує доступ у браузері; надсилати
паролі, токени або ключі в чат не потрібно.

На своєму Windows ПК відкрийте PowerShell і виконайте:

```powershell
Invoke-WebRequest -Uri 'https://raw.githubusercontent.com/windroye590-create/litakova-updates/main/release-tools/setup-automation.ps1?portable=1' -OutFile "$env:TEMP\litakova-setup-automation.ps1" -ErrorAction Stop; if ($?) { powershell.exe -NoProfile -ExecutionPolicy RemoteSigned -File "$env:TEMP\litakova-setup-automation.ps1" }
```

[Переглянути скрипт перед запуском](../release-tools/setup-automation.ps1).
Параметр `RemoteSigned` діє лише для цього процесу PowerShell.

Скрипт:

1. За потреби завантажує закріплені portable-версії GitHub CLI та Node.js
   з офіційних сайтів, перевіряє SHA-256 та розпаковує в
   `%LOCALAPPDATA%\LitakovaReleaseTools`. `winget` і права адміністратора
   не потрібні. PATH змінюється лише всередині процесу налаштування.
2. Відкриває вхід GitHub, якщо він ще не налаштований, і перевіряє право
   керувати секретами саме `windroye590-create/litakova-updates`.
3. Пропонує вибрати оригінальний `Litakova-Komisiia-v1.4.1-source-and-signing.zip`.
   Ключ і пароль читаються з ZIP у пам'ять; код з цього старого архіву не використовується.
4. Відкриває [налаштування Apps Script API](https://script.google.com/home/usersettings).
   Увімкніть API та натисніть Enter у PowerShell.
5. Запускає закріплений `clasp 3.4.1` для входу власника скрипту. Вхід
   зберігається як окремий обліковий запис `litakova-release`; інші облікові
   записи з локального файлу авторизації не передаються.
6. Через stdin GitHub CLI записує три захищені секрети: `GAS_CREDENTIALS`,
   `LK_SIGNING_PKCS12_BASE64`, `LK_SIGNING_PASSWORD`.
7. Запускає перевірку реального доступу Google та оригінального сертифіката.
   Ця перевірка читає сервер, але не розгортає код і не змінює базу.

Замість діалогу вибору можна вказати архів параметром
`-SigningArchive 'C:\шлях\Litakova-Komisiia-v1.4.1-source-and-signing.zip'`.

[Результат перевірки підключення](https://github.com/windroye590-create/litakova-updates/actions/workflows/verify-release-automation.yml).
До успішної перевірки реальних облікових даних налаштування розгортання
не вважається завершеним.

## Звичайний випуск

1. Внесіть зміни у `source/` та опишіть їх у `next-release-notes.md`.
2. Дочекайтеся успішної перевірки коду в main.
3. Відкрийте [«Випустити EXE та Apps Script»](https://github.com/windroye590-create/litakova-updates/actions/workflows/release.yml),
   натисніть **Run workflow**, залиште гілку **main** та введіть нову версію,
   наприклад `1.2.28`.

Код збірки обчислюється за підписаним каталогом останнього публічного випуску.
Процес узгоджує `package.json`, frontend, native та серверні константи,
виконує тести логіки й браузерні перевірки, збирає Windows EXE та перевіряє
його вбудовані ресурси. PE створюється без поточної часової мітки, тому
повторне збирання в однаковому середовищі дає ті самі байти.

Підпис виконується оригінальним RSA-3072 ключем. Сертифікат звіряється з
ключем, якому вже довіряють установлені програми. Тимчасові приватні файли
залишаються в окремій тимчасовій папці runner і видаляються після підпису.

Перед записом на сервер процес перевіряє, що main не змінився, та зберігає
в Git перевірені джерела, ZIP коду й кандидат випуску. Підготовлений кандидат
може бути в Git до публікації; автооновлення використовує лише **Releases/latest**.
Тег випуску посилається на коміт підготовлених джерел.

Apps Script читається через API. Якщо логіка сервера змінилася, оновлюється
лише визначений файл сервера; зберігаються інші файли, manifest, поточний
deployment ID та його адреса й доступ. Повторне початкове налаштування
комісії не запускається. Самі зміни номера EXE не спричиняють розгортання.

## Зупинка та відновлення

Неопубліковані серверні правки, виявлені перед оновленням, зупиняють випуск.
Повторна перевірка перед записом також зупиняє процес, якщо проєкт змінився
після початкового читання. Редагувати Apps Script під час випуску не слід:
Apps Script API не надає атомарного блокування сторонніх редакторів.

Якщо запис, оновлення розгортання або перевірка нового сервера завершилися
обробленою помилкою, процес намагається повернути попередню версію
розгортання й вихідний код та перевіряє старий сервер. Він не перезаписує
виявлені нові правки іншого редактора; у такому разі журнал повідомляє,
що повернення потребує уваги. Попередні версії залишаються в Apps Script.

EXE публікується лише після успішної перевірки сервера. У чернетці GitHub
перевіряються всі чотири файли; лише після цього перемикається latest.
Якщо публікація GitHub перервалася, сервер автоматично не відкочується:
новий EXE уже міг стати доступним. Частковий випуск залишається для відновлення,
а підтверджений сервер має бути сумісним зі старими клієнтами.

Примусове завершення runner не гарантує виконання обробника повернення.
Журнал містить попередню версію розгортання для відновлення через Apps Script.
Зміни даних у таблицях цим процесом не відкочуються. Зміна API або бази
потребує окремого оновлення правил сумісності в `automation.json`.

Історичні workflow окремих версій збережено в `release-staging/legacy-workflows/`.
Активний шлях публікації один — `release.yml`.
